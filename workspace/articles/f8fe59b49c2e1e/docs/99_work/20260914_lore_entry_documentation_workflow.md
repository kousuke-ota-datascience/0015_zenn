- `<4桁ゼロ埋めEntry_ID>_10_analysis.md`

# 1. 全体ワークフロー

1件の伝承エントリは、原則として次の順序で処理する。

```text
0. 対象Entryの確定
1. 方針ドキュメントの読み込み
2. 典拠調査・Evidence整理
3. *_00_contents.md の作成
4. Version Scope・分析条件の固定
5. *_10_analysis.md の作成
6. 00 / 10 横断QA
7. GitHub反映・push後検証
8. パイロット49件のみ control plane 更新
```

重要なのは、`00_contents` と `10_analysis` を単にテンプレートへ機械的に入力することではない。

```text
原資料・証拠
→ 証拠に忠実な伝承記録
→ 分析対象Versionの固定
→ 21概念次元による分析
→ コード
```

というトレーサビリティを保持することを目的とする。

# 2. Step 0 — 対象Entryの確定

## 2.1. Entry_IDを確認する

作業開始時に、対象伝承の `Entry_ID` を正本データから確認する。

ディレクトリ・ファイル名は必ず4桁ゼロ埋めする。

```text
<4桁ゼロ埋めEntry_ID>_<伝承識別名>/
├── <4桁ゼロ埋めEntry_ID>_00_contents.md
└── <4桁ゼロ埋めEntry_ID>_10_analysis.md
```

独自に番号を振ってはならない。

## 2.2. 1 Entryの分析単位を確認する

伝承エントリは、

> 人々が異常・不可解・不確実な何かを理解可能なものへ変換するために共有する、独立して伝達可能な最小の意味形成モデル

とする。

以下だけを理由にEntryを分割してはならない。

- 登場人物・被害者が複数いる
- 典拠が複数ある
- 地域名や人物名が異なる
- 被害人数や細部が異なる
- 1次元で複数Secondaryが必要になる
- 同一世界規則の軽微な異伝が存在する

一方、以下が安定して異なり、世界のルールそのものが変わる場合は別Entry候補とする。

- 何を説明対象とするか
- 何を原因として置くか
- 何を発動条件とするか
- 何に作用するか
- どのように作用するか
- どのような帰結を持つか
- どのような回避・制御規則を持つか

Entry境界に疑義がある場合、調査前に無理に分割せず、まずEvidenceを集める。調査後も安定して世界規則が異なる場合に分割候補として扱う。

毎Entryで全文を機械的に再読する必要はないが、作業セッション開始時、正本更新後、コード境界に疑義が生じた場合は最新版を再取得する。

## 3.1. `10_urban_legend_analysis_axes_theoretical_design.md` で確認すること

この文書では、主として以下を確認する。

- 研究目的は「怪異の種類の分類」ではなく、sense-making modelの比較であること
- 分析単位が1伝承エントリであること
- 21概念次元が何を互いに区別して測るのか
- 類似して見える次元間の理論的境界
- Primary / Secondaryは次元数を増やすものではないこと
- `U / NA / C` は値ではなくDimension Statusであること

特に、既存のMacro Category、旧分類、物語ジャンルからD07〜D21を逆算してはならない。

## 3.2. `20_urban_legend_parent_child_code_system.md` で確認すること

この文書では、主として以下を確認する。

- 各D次元のデータ型 `S / O / H1 / H3 / B`
- 使用可能なChild / Value ID
- ChildからParentへの対応
- Primary / Secondaryの定義
- Secondaryに入れてよい構造と、単なる背景・言い換えの違い

H3ではPrimaryはexactly 1、Secondaryは0〜2とする。

Parentは独立に判断してはならない。**Childを決めた後、コード体系から機械的にParentを導出する。**

`0000_10_analysis.md` には `Primary Parent` 欄があるため値は記録するが、分析者が別判断して決める値ではない。

既存Childに入らない安定構造が見つかった場合、その場で独自コードを作らない。コードブック改訂候補として別途扱う。

## 3.3. `30_urban_legend_analysis_coding_rules.md` で確認すること

この文書では、主として以下を確認する。

- Evidence role
- Evidenceの優先順位
- Dimension Status
- コーディング順序
- 各Dのinclude / exclude境界
- D02、D03、D16、D18等の誤判定しやすい境界

Evidence roleは次の4つを区別する。

| Role | 用途 |
|---|---|
| `C` Content | 伝承内容、条件、作用、帰結、時間構造 |
| `H` History | 成立・流通年代、媒体、変容史 |
| `X` External effect | 現実社会で実際に生じた行動・制度・市場等の効果 |
| `A` Anchor | 実在地・制度・史実との接続 |

同一資料が複数roleを持ってよい。

Dimension Statusは次のとおり。

- `D`: 典拠に直接明示
- `I`: 定義と証拠から合理的に推定
- `U`: 資料不足
- `NA`: 伝承構造上非該当
- `C`: 同一Version Scope内で主要形が競合

最重要原則は、**`U` を最もありそうな値で埋めないこと**である。

## 3.4. `90_ducumentation_metadata.md` で確認すること

この文書では、主として以下を確認する。

- Entry_IDとディレクトリ・ファイル命名
- 文書責務の分離
- 正本間の優先順位
- 見出し・文書構造規則

個別伝承の理論・コード判断を `90` から導かない。

# 4. Step 2 — 典拠調査・Evidence整理

`00_contents.md` を書き始める前に、対象Entryについて必要なEvidenceをまとめて調査する。

D01〜D21を1次元ずつ検索してはいけない。まず伝承全体のEvidence mapを作り、その後の分析で不足している境界だけ追加調査する。

## 4.1. 最低限集める情報

少なくとも次の観点を調べる。

### 4.1.1. Content

- 代表的な伝承内容
- 発端または適用条件
- 異常・中心命題
- 因果説明
- 行為・対応
- 帰結
- 回避・制御方法
- 伝承内で明示されない部分

### 4.1.2. History

- 現在確認できる最古資料
- 最古確認流通媒体
- 流通地域・共同体
- 媒体移行
- 異伝の出現時期
- 反証・再解釈・創作化・再流通

### 4.1.3. Variants

- 共有核
- 主要異伝
- 後代追加要素
- 地域化
- 因果源の差
- 発動条件の差
- 帰結の差
- 回避規則の差

### 4.1.4. External effects

D18 L3候補となり得る場合のみ、噂の流通によって現実社会で確認可能な結果が生じたかを調べる。

例:

- 行政対応
- 警察・学校対応
- 買い占め
- 商品売上変動
- 観光行動
- 差別・暴力
- 制度変更
- 実務慣行

「起きそう」では足りない。X evidenceが必要である。

### 4.1.5. Anchors

- 実在地
- 実在人物
- 実在制度
- 実在事件
- 歴史記録
- 地質・医学・工学等の事実

実在することと、伝承内の主張が真であることを混同しない。

## 4.2. 典拠優先順位

原則として以下を優先する。

1. 原投稿・同時代一次記録・公式文書
2. 原著論文・民俗採録・同時代報道の再掲
3. 高品質な書誌・研究書・専門家による歴史整理
4. 信頼できる二次資料
5. その他の解説

一次資料が見つからないこと自体は作業停止理由ではない。

その場合は、

- 一次資料未確認であること
- どの二次資料に依存するか
- どの主張まで安全に言えるか

を明示する。

## 4.3. やってはいけないこと

- 検索結果snippetだけで詳細内容を確定する
- 書誌ページが存在するだけで本文内容を読んだことにする
- 後代まとめサイトだけから初期形を復元する
- 有名な後代設定を初期資料へ遡及する
- 「古い伝承だから口承」と推定する
- 「ネット発祥ではないから口コミ」と推定する
- 反証記事が存在するだけで最古流通媒体をその媒体にする
- 現実の事故・死亡等を、伝承が因果付けていないのに伝承内容へ組み込む
- 一つの資料だけで全異伝・全時代を代表させる

## 4.4. 調査の終了条件

無限に資料を探し続けない。

以下が揃えば、原則として `00_contents` 作成へ進む。

- 共有核を再構成できる
- 主要異伝を区別できる
- 現在確認できる最古資料を特定、または特定不能と明示できる
- 主要な流通媒体を確認できる、または不明と明示できる
- 実在アンカーを必要範囲で確認できる
- D07〜D18の判断に必要な内容Evidenceが概ね揃う

不足部分は `U` や保留事項として保持してよい。

## 5.3. `1.1. summary` の書き方

summaryは辞書的な2〜3文では不十分である。

目的は、**原典を毎回開き直さなくても、その伝承で何が起きる／何が主張されるのかを再構成できる高密度パラフレーズ**を残すことである。

### 5.3.1. 時間的進行を持つ伝承

少なくとも以下を追えるようにする。

- 発端
- 最初の異常
- 展開・反復・拡大
- 主体の対応
- 転換・エスカレーション
- 明示的終端
- 未解決点

人物・場所・物・行為・順序・因果主張を残し、後続のD07〜D17を再検討できる密度にする。

### 5.3.2. 非時間的伝承

俗信・ジンクス・命題型噂・制度俗説では時系列を無理に作らない。

少なくとも以下を記述する。

- 対象状況
- 適用条件
- 中心命題・規則
- 因果説明
- 想定作用
- 帰結
- 回避・制御・利用方法
- 証拠上確認できる範囲

## 5.4. `1.2. 詳細展開`

summaryを分解し、後から参照できる構造にする。

物語型なら時系列、命題型なら原則として

```text
条件
→ 主張／規則
→ 想定作用
→ 帰結
```

の順で整理する。

可能なら頁、レス番号、記事日付、採録番号等を付ける。

## 5.5. `1.3`〜`1.10`

以下を明確に分離する。

- `1.3`: 誰／何が登場するか
- `1.4`: どこで起きるか、実在／比定／架空／不明
- `1.5`: 作用や伝達に重要な物・記号・媒体
- `1.6`: 条件・規則・禁忌・対処・利用
- `1.7`: 何が異常／中心命題なのか
- `1.8`: 主体が何をするか
- `1.9`: 明示帰結・暗示帰結・確認されない帰結
- `1.10`: 何が不明・競合・後代解釈依存なのか

特に `1.9` では、

- 投稿が止まる
- その後不明
- 連絡不能

を、証拠なしに死亡・失踪へ変換しない。

## 5.6. `2.1`〜`2.4`

「伝承の起源」と「現在確認できる最古資料」を必ず分ける。

`2.2` では、確認できない流通経路を補完しない。

`2.3` では、異伝を表形式等で比較し、時期・媒体・地域・共有核との差を残す。

`2.4` では、

- 意味形成対象
- 因果源
- 発動条件
- 作用
- 帰結
- 回避規則

のどこが変化したかを見る。

## 5.7. `3.1`〜`3.3`

`3.1` は主要な主張と典拠を対応させる。

`3.2` の原文引用は必要最小限とし、長文転載しない。

`3.3` には、後続分析で `U / C` となり得る証拠限界を明示する。

## 5.8. `00_contents` で禁止すること

- Candidate Masterの短文を言い換えただけにする
- コード定義を散文へ変換しただけにする
- 原資料にない心理を補う
- 原資料にない真相を補う
- 原資料にない因果関係を補う
- 原資料にない結末を補う
- 後代設定を初期Versionへ混入する
- 分析コードを本文へ混ぜる
- Evidenceの弱さを隠す

「文書が厚い」ことと「証拠が強い」ことは別である。

# 6. Step 4 — Version Scope・分析条件の固定

`00_contents` を作成した後、`10_analysis` のコーディング前に分析対象を固定する。

## 6.1. `Version_Scope` を明示する

Version Scopeには、少なくとも以下が分かるようにする。

- どの時期の伝承形を含むか
- どの媒体の伝承形を含むか
- 共有核として何を含むか
- どの主要異伝を含むか
- どの後代派生を除外するか
- どの創作・翻案を除外するか

Version Scopeは「このEntryで今回何をコードするか」の境界である。

異伝を全部混ぜて最大公約数的な怪物を作ってはならない。

逆に、共有核を無視して一つの偶発的な再話だけへ狭めすぎてもならない。

## 6.2. `Entry_Type` と `Macro_Category`

正本・既存分類が存在する場合はそれを確認する。

これらをD07〜D21の推定根拠として使用してはならない。

分類は分析結果を導くものではなく、別の管理・比較軸である。

## 6.3. Family_ID等の補助情報

データセット側でFamily_ID等を使用している場合は整合性を確認する。ただしtutorialに存在しない独自フィールドを `10_analysis.md` の基本情報へ追加しない。

## 7.3. コーディングの思考順

実際の判定はcoding rulesどおり以下の順で行う。

```text
1. Entry_ID / Entry_Type / Version_Scopeを固定
2. D07 意味形成対象
3. D08 意味形成契機
4. D09 意味付与操作
5. D10 因果源存在論
6. D11 発動・接触条件
7. D12 作用対象
8. D13 作用機構
9. D14 帰結極性
10. D15 帰結領域
11. D16 因果時間構造
12. D17 回避・制御方式
13. D18 作用レイヤー
14. D01〜D06 来歴・提示
15. D19〜D21 社会的埋め込み・現実アンカー
```

**分析の思考順と、完成文書の記載順は異なる。**

完成した `10_analysis.md` はtutorialどおりD01からD21の順で記録する。

これにより、

- 古い話だから口承
- 地域伝承だから地元住民が真相保持者
- 怪談だから超自然原因

といった、カテゴリや来歴から内容構造を逆算する誤りを防ぐ。

## 7.4. 各Dの正規形

各次元は原則として以下を使用する。

```text
- Primary Child / Value:
- Primary Parent:
- Secondary:
- Status:

**判定根拠**

...

**この伝承における現れ方**

...
```

使用しない表現:

- `Primary:`
- `Value:`
- `Primary Child:`
- `Secondary 1 Child:`
- `Secondary Parent:`
- `現れ方:`
- 独自の末尾パイロットメモ

## 7.5. `判定根拠` に書くこと

### Dの場合

- 何が典拠に直接明示されているか
- `00_contents` のどの資料・内容が支えるか

### Iの場合

- どのEvidenceがあるか
- どのコード定義を適用したか
- どこが推論なのか

### Uの場合

- 何が確認できないのか
- 何を推定してはいけないのか

### NAの場合

- なぜ伝承構造上その次元が成立しないのか

### Cの場合

- どのVersion・資料・異伝が競合するか
- なぜPrimaryを一つへ閉じられないか

`U / NA / C` でも説明を空欄にしない。

## 7.6. `この伝承における現れ方` に書くこと

コード定義の言い換えではなく、伝承固有の

- 人物
- 場所
- 物
- 主張
- 条件
- 行為
- 因果関係
- 帰結

を使って、なぜその分析概念になるかを書く。

例えば `SPATIAL_DISTORTION` なら「空間異常だから」と書いて終えず、具体的にどの経路・接続・距離・位置関係が通常世界のルールから外れるかを書く。

目標は、

```text
原資料上の具体的展開
→ 分析者の解釈
→ コード
```

を後から第三者が追跡できることである。

## 7.7. Primary / Secondary

Primaryは、その次元においてEntryの意味形成構造を最も強く規定するChildとする。

Secondaryは、Primaryを除いてもなお残る独立した追加構造である。

以下はSecondaryにしない。

- Primaryの言い換え
- 背景設定
- 舞台
- 帰結を別表現しただけのもの
- 少し関連するだけの要素

## 7.8. 特に注意する次元

### 7.8.1. D01

最古確認年と生成年代を混同しない。

「遅くとも1994年に存在した」だけでは1990年代生成と断定できない場合がある。

安全に年代帯へ写像できなければ `U`。

### 7.8.2. D02

D02は起源媒体ではない。

> 現在の証拠で、伝承が実際に人から人へ流通したことを最も古く確認できる媒体

をコードする。

禁止:

- 古いから口承
- 非ネット発祥だから口承
- FOAFだから口承
- 後代事典に載ったから書籍が最古

### 7.8.3. D03

Version Scope内で実際に確認できる媒体だけをコードする。

現在Web検索で見つかるという理由だけでWebを付けない。

研究DB・ファクトチェック記事を、伝承流通媒体と混同しない。

### 7.8.4. D04

変容を示すHistory Evidenceがない場合、安易に `STABILIZED_CANON` や単発固定へ閉じない。

異伝比較・媒体移行・反証・増補・地域化等のEvidenceが必要である。

### 7.8.5. D05 / D06

D05は「どの形式で伝承が提示されるか」。

D06は「どのような真実性を要求するか」。

研究者が真偽を知っていることと分離する。

誤った科学説でも、一般的な科学事実として提示されるならD06はその提示態度をコードする。

### 7.8.6. D07 / D08

D07では、

> この伝承がなければ、何が説明されないまま残るか

を先に文章化する。

D08はその不可解さを問題化する手掛かりであり、D11の発動条件とは別である。

### 7.8.7. D09 / D10

D09は、不可解な対象を理解可能にする認知操作。

D10は、その説明の中で何を因果源として世界に置くか。

「原因帰属」と「原因そのもの」を混同しない。

### 7.8.8. D11 / D12 / D13

D11 = 因果系へ入る条件。

D12 = 何が作用されるか。

D13 = 因果源が対象へ何をするか。

D13で資料不足を `MANIFEST_ONLY` にしない。`MANIFEST_ONLY` は、伝承構造上追加作用が不要な場合にのみ使用する。

### 7.8.9. D14 / D15

D14は主帰結の正負。

D15は最終的に何の領域が変わるか。

作用機構D13と結果D15を混同しない。

語りが途絶えただけで `DEATH` や `DISAPPEARANCE` を付けない。

### 7.8.10. D16

D16は伝承の流通期間ではなく、伝承内の因果時間構造である。

非物語型・静的命題を `U` にしない。

- 静的対応・属性・規則 → STA
- 1エピソード内進行 → EVT
- 待ち時間・期限 → DLY
- 徐々に進行 → PRG
- 再発 → REC
- 持続 → CON
- 対象間伝播 → TRN

### 7.8.11. D17

対処法が資料にないから「不可避」としてはならない。

不可避には明示証拠が必要である。

現実世界の一般的安全対策を、伝承固有の回避規則へ勝手に入れない。

### 7.8.12. D18

- L1: 伝承内容内部の因果作用
- L2: 読む・聞く・受信する現実側受容者が、伝承内容上の因果対象になる
- L3: 噂の流通によって、現実社会で観測可能な行動・制度・市場等の結果が生じる

L2は、単に話を聞いて怖くなった／行動を変えたことではない。

L3にはX evidenceが必要である。

### 7.8.13. D19

「どの媒体で流通したか」ではなく「どの社会範囲まで流通したか」を測る。

D03と混同しない。

### 7.8.14. D20

単に噂を知っている人ではなく、真相・追加情報・回避情報を偏って保持する主体をコードする。

`NO_ONE_KNOWS` は「伝承内に真相保持者が存在しない」という強い主張なので濫用しない。

### 7.8.15. D21

資料が実在することと、伝承内容が現実世界へアンカーされていることを分離する。

実在地や実在人物を舞台として使用するだけなのか、実在制度・史実・既存伝統が伝承の因果モデルに不可欠なのかを区別する。

# 10. 作業効率の標準規則

400件以上を処理するため、精度を落とさず無駄なツール往復を減らす。

## 10.1. 方針文書はまとめて読む

1 Entryごとに21コードを逐次検索し直さない。

作業セッション開始時に、

- 10
- 20
- 30
- tutorial 00
- tutorial 10

をまとめて確認する。

個別Entryでは、**判断が曖昧なコード境界だけ**再検索する。

## 10.2. Evidenceを先にまとめる

悪い流れ:

```text
D01を調べる
→ D02を調べる
→ D03を調べる
→ ...
→ D21を調べる
```

標準の流れ:

```text
伝承全体のEvidenceをまとめて調べる
→ 00_contentsで証拠構造を固定する
→ D07〜D18を一括判定する
→ 来歴・社会次元を判定する
→ 曖昧な次元だけ追加調査する
```

## 10.3. 不明を許容する

すべてのDをD/Iで埋めることを品質目標にしない。

証拠が不足するなら `U` が正しい。

調査時間を費やして「最もありそうな値」を探すことは、精度向上ではなく推測の増加になり得る。

## 10.4. 追加調査の優先順位

追加調査は以下の場合に限定して優先する。

- Entry境界が変わる可能性がある
- Version Scopeが決められない
- D07〜D18の意味形成核が変わる
- D02の最古媒体が大きく変わる
- D04の変容モデルが変わる
- D18 L3の有無が変わる
- D21の現実アンカー強度が変わる

細部の装飾設定だけを確定するために過剰調査しない。

# 13. 代表的な失敗パターン

## 13.1. 薄い文書

症状:

- 00が数段落だけ
- 10がコード一覧だけ

対策:

Evidenceから意味形成構造を再検討できる自然言語情報を残す。

## 13.2. EvidenceとAnalysisの混在

症状:

- 00にDコードを書く
- 10に長い原典転載を書く

対策:

00 = Evidence / Content、10 = Analytical definition / Codingを厳守する。

## 13.3. 後知恵の遡及

症状:

- 後代の有名設定を最初期版へ入れる
- 現在の創作イメージで古い資料を読む

対策:

時期・媒体・異伝を分離し、Version Scopeで境界を固定する。

## 13.4. 不明値の推測補完

症状:

- 古いから口承
- 怪談だから超自然原因
- 投稿停止だから失踪

対策:

Evidenceがなければ `U`。分析者の常識で穴埋めしない。

## 13.5. コード表の逐次検索で作業が肥大化

症状:

21次元を1件ずつ検索し、同じコード表を何度も開く。

対策:

Evidenceを先にまとめ、コード体系はセッション単位で読み込み、曖昧な境界だけ再照合する。

## 13.6. 1 Entryに複数世界規則を混ぜる

症状:

同名だからという理由で、原因・発動・帰結の異なる異伝を一つに混ぜる。

対策:

意味形成核が安定して異なる場合は別Entry候補とする。

## 13.7. 複数Entryを同一commitへ混ぜる

症状:

差分検証が困難になり、中途状態のファイルが混入する。

対策:

1 Entry = 1 commitを原則とする。
