# 0. INTRODUCTION

本書は、`docs/10_each_lore/` 配下で1伝承エントリの `*_00_contents.md` と `*_10_analysis.md` を作成・更新・検証するための**標準作業手順（workflow）**である。

本書は、A3パイロット49件に限定されない。今後の400件以上の伝承調査を含め、個別伝承エントリを同一基準で文書化・分析する際の共通インストラクションとして用いる。

本書は理論・コード体系・コーディング規則そのものを再定義しない。責務の正本は以下とする。

- 理論設計: `docs/00_research_overview/10_urban_legend_analysis_axes_theoretical_design.md`
- コード体系: `docs/00_research_overview/20_urban_legend_parent_child_code_system.md`
- コーディング規則: `docs/00_research_overview/30_urban_legend_analysis_coding_rules.md`
- 文書管理・命名規則: `docs/00_research_overview/90_ducumentation_metadata.md`
- `00_contents` 記載様式: `docs/10_each_lore/0000_tutorial/0000_00_contents.md`
- `10_analysis` 記載様式: `docs/10_each_lore/0000_tutorial/0000_10_analysis.md`

本書と上記正本が競合した場合、各責務の正本を優先し、本書側を修正する。

# 1. 標準ワークフロー全体像

1伝承エントリは、原則として以下の順序で完結させる。

```text
Step 0. 対象Entryと分析単位を確定
→ Step 1. 方針ドキュメント・tutorialを読み込む
→ Step 2. 典拠調査とEvidence整理
→ Step 3. *_00_contents.md を作成
→ Step 4. Version Scopeと分析条件を固定
→ Step 5. D01〜D21をコーディングし *_10_analysis.md を作成
→ Step 6. 00 / 10 横断QA
→ Step 7. GitHub反映・push後検証
→ Step 8. 必要なプロジェクト固有の進捗管理を更新
```

重要なのは、**Evidenceを集める工程とコーディング工程を混ぜないこと**である。D01を判定するたびに検索し、次にD02のため再検索する、という進め方は避ける。まず当該伝承の主要Evidenceをまとめて確保し、`00_contents` に整理してから分析へ進む。

# 2. Step 0 — 対象Entryと分析単位を確定

## 2.1. Entry_IDの確認

作業開始前に対象の `Entry_ID` を正本データから確認する。

個別伝承ディレクトリと主要ファイルは次の形式とする。

```text
<4桁ゼロ埋めEntry_ID>_<伝承識別名>/
├── <4桁ゼロ埋めEntry_ID>_00_contents.md
└── <4桁ゼロ埋めEntry_ID>_10_analysis.md
```

`0000` はtutorial専用であり、実伝承へ使用しない。

## 2.2. 1伝承エントリの境界

分析単位は「独立して伝達可能な最小の意味形成モデル」である。

人物名・地名・被害人数・媒体・表現上の細部が違うだけでは通常はEntryを分割しない。

一方、以下が安定して変わり、**世界のルールそのものが変わる**場合は別Entry候補とする。

- 何を説明対象とするか
- 何を原因として置くか
- 発動・接触条件
- 作用対象
- 作用機構
- 主帰結
- 回避・制御規則

疑わしい場合は、先に複数Entryへ分割してしまわず、主要異伝を `00_contents` に保持し、Version Scopeを決める段階で境界を再検討する。

# 3. Step 1 — 方針ドキュメント・tutorialの読み込み

作業開始時に少なくとも以下を確認する。

- `10_urban_legend_analysis_axes_theoretical_design.md`
- `20_urban_legend_parent_child_code_system.md`
- `30_urban_legend_analysis_coding_rules.md`
- `0000_00_contents.md`
- `0000_10_analysis.md`

必要に応じて `90_ducumentation_metadata.md` も確認する。

読み込みの目的は、単にファイルを参照したことにすることではない。以下を明示的に確認する。

- 研究目的が「怪異分類」ではなくsense-making modelの比較であること
- Parent / Child / Primary / Secondaryの関係
- `D / I / U / NA / C` の意味
- D01〜D21の中心質問
- Evidence role (`C / H / X / A`)
- `00_contents` と `10_analysis` の責務分離
- tutorialの章構造・項目名・順序

旧コード・Macro Category・ジャンル名から新コードを逆算してはならない。

# 4. Step 2 — 典拠調査とEvidence整理

## 4.1. 先にEvidenceをまとめて確保する

1伝承について、可能な範囲で以下をまとめて調査する。

- 伝承内容そのもの
- 最古確認資料
- 流通媒体
- 流通範囲
- 異伝・派生
- 変容史
- 現実社会への外部効果
- 実在地・史実・制度等の現実アンカー

D01〜D21を一つずつ検索してはいけない。先にEvidence集合を構築し、その後まとめてコードする。

## 4.2. Evidence role

資料は用途を意識して整理する。

- `C` Content: 伝承内容、条件、作用、帰結、物語展開
- `H` History: 成立、流通年代、媒体、変容史
- `X` External effect: 噂の流通によって現実社会で実際に起きた効果
- `A` Anchor: 実在地、制度、史実、自然科学的背景等

同じ資料が複数roleを持ってよい。

## 4.3. 証拠優先順位

原則として次を優先する。

1. 原投稿・同時代一次記録・公式文書
2. 原文に近いミラー・転載・復刻・原著論文・民俗採録
3. 高品質な研究書・専門家整理・信頼できる二次資料
4. 後代のまとめ・解説

一次資料が確認できない場合でも調査不能とはしない。ただし、一次資料未確認であることを明示し、後代資料から過度に遡及しない。

## 4.4. やってはいけないこと

- 書籍販売ページや書誌ページだけで物語細部を直接確認したことにする
- 後代の有名な設定を最初期形へ遡及させる
- 「古い伝承だから口承」と推定する
- 「ネット発祥でないから口コミ」と推定する
- 反証資料があることを、伝承が存在しなかった証拠とみなす
- 実在する場所・事件・制度があることを、そのまま伝承上の因果関係の事実とみなす
- 文書が詳細であることと、Evidenceが強いことを混同する

# 5. Step 3 — `*_00_contents.md` の作成

`0000_00_contents.md` の章構造・項目名・順序に従う。

`00_contents` は **Evidence / Content layer** であり、分析コードを決める場所ではない。

## 5.1. `00_contents` に書くもの

- 伝承内容
- 典拠
- 伝承史
- 異伝・派生
- 資料間の差
- 一次資料と後代再話の差
- 証拠上の不確実性
- 現実アンカーの事実関係
- 外部効果を示す証拠

## 5.2. 原則として書かないもの

- `Entry_ID`
- `Macro_Category`
- `Entry_Type`
- `Version_Scope`
- D01〜D21のコード値

## 5.3. `1.1 summary` の要求密度

summaryは辞書的な2〜3文で終えない。

### 5.3.1. 時間的進行を持つ伝承

少なくとも次が追える密度にする。

- 発端
- 異常の顕在化
- 展開
- 登場人物の対応
- 転換／エスカレーション
- 終端
- 未解決部分

### 5.3.2. 非時間的な伝承

俗信・制度俗説・ジンクス・命題型噂等では、時系列を無理に作らず、次を整理する。

- 対象状況
- 成立条件
- 中心命題・規則
- 因果説明
- 想定作用
- 帰結
- 回避・制御・利用方法
- どこまでがEvidenceでどこからが推測か

## 5.4. summaryで禁止すること

- Candidate Master等の短い要約を言い換えるだけ
- コード定義を文章化するだけ
- 原資料にない心理・真相・因果・結末を補う
- 「投稿が途絶えた」を死亡・失踪と同一視する
- 後代版の要素を初期Versionへ混ぜる

## 5.5. `1.2`〜`3.3` の役割

summaryだけを厚くして終わらない。

- `1.2 詳細展開`: 時系列または論理展開を分解
- `1.3 登場人物・主体`: 誰が何の役割を持つか
- `1.4 場所・空間`: 実在／比定／架空／不明を区別
- `1.5 物・記号・媒体`: 因果や展開に必要な物を整理
- `1.6 条件・規則・禁忌`: 発動、禁止、対処、回避、利用
- `1.7 異常・不可解な現象／中心命題`
- `1.8 行動・対応`
- `1.9 帰結・終端状態`: 明示／暗示／未確認を分離
- `1.10 未解決点・不確実性`
- `2.1 最古確認`: 起源と最古確認資料を区別
- `2.2 流通・拡散`
- `2.3 主要な異伝・派生`
- `2.4 変容上の重要点`
- `3.1 内容と典拠の対応表`
- `3.2 短い原文引用`: 必要最小限
- `3.3 証拠上の保留事項`

`00_contents` 単独で、後から原典を毎回開き直さなくても主要構造とEvidence限界を再構成できる状態を目指す。

# 6. Step 4 — Version Scopeと分析条件の固定

`00_contents` が完成したら、`10_analysis` の作成前に **Version Scopeを固定する**。

Version Scopeは、当該Entryで「どの伝承形・どの期間・どの媒体層までを一つの分析対象としてコードするか」を明示する分析条件である。

## 6.1. Version Scopeに含めるもの

- 共有核を構成する主要形
- 当該Entryの意味形成モデルを維持する主要異伝
- 分析上必要な流通・変容層

## 6.2. 分離するもの

- 後代の創作翻案
- 世界のルールを変える安定異伝
- 原型と因果源・発動条件・作用・帰結が異なる派生
- Evidenceが弱く、共有核とみなせない有名設定

## 6.3. Version Scope固定前にコードしない

異伝を広く集めた `00_contents` と、実際にコードする範囲は同一ではない。

Scopeを固定せずにD07〜D18を決めると、初期形と後代派生が混ざるため禁止する。

# 7. Step 5 — `*_10_analysis.md` の作成

`0000_10_analysis.md` の構造・項目名・順序へ厳密に従う。

`10_analysis` は **Analytical definition / Coding layer** である。

## 7.1. 基本情報

基本情報はtutorialで定められた以下のみとする。

```text
- Entry_ID
- 伝承エントリ名称
- Macro_Category
- Entry_Type
- Version_Scope
```

独自の `Evidence_Rank`、`ネット発祥`、`主な成立・流通期` 等を追加しない。

## 7.2. コーディングの思考順と記載順を分ける

### 分析時の推奨順

`30_urban_legend_analysis_coding_rules.md` に従い、原則として次の順で判定する。

```text
D07 → D08 → D09 → D10
→ D11 → D12 → D13 → D14 → D15 → D16 → D17 → D18
→ D01 → D02 → D03 → D04 → D05 → D06
→ D19 → D20 → D21
```

意味形成・因果構造を先に捉え、来歴やジャンルから内容構造を逆算しない。

### 完成文書の記載順

`0000_10_analysis.md` に従い **D01 → D21** の順に記載する。

## 7.3. 各次元の記載内容

各Dで原則として次を記載する。

```text
- Primary Child / Value:
- Primary Parent:
- Secondary:
- Status:

**判定根拠**
...

**この伝承における現れ方**
...
```

## 7.4. 「判定根拠」

以下が追えるように書く。

- `00_contents` のどのEvidenceが根拠か
- `D` なら何が直接明示されるか
- `I` なら何とコード定義から推論したか
- `U` なら何が不足しているか
- `NA` ならなぜ構造上成立しないか
- `C` なら何と何が競合しているか

## 7.5. 「この伝承における現れ方」

コード定義の言い換えではなく、伝承固有の人物・場所・出来事・条件・行為・帰結を使う。

目標は、

```text
原資料上の具体的内容
→ 分析者の解釈
→ コード
```

のトレーサビリティを残すことである。

## 7.6. Primary / Secondary

- Primaryは、その次元で意味形成構造を最も強く規定するChild
- Secondaryは、Primaryだけでは失われる独立した追加構造
- 「少し関係する」だけの要素はSecondaryにしない
- H3ではPrimary exactly 1 (`D/I`時)
- Secondaryは0〜2

ParentはChildから導出される。独立に判断しない。

## 7.7. Status

- `D`: 典拠に直接明示
- `I`: Evidenceと定義から合理的に推定
- `U`: 資料不足
- `NA`: 構造上非該当
- `C`: 同一Scope内で競合

`U` を最もありそうな値で埋めてはならない。

# 8. Step 5で特に注意する次元

## 8.1. D01

最古確認年と生成年代を混同しない。

「遅くとも2008年に存在」は「2000年代に生成」とは限らない。安全に年代帯へ写像できなければ `U`。

## 8.2. D02

起源媒体ではなく、**現在の証拠で最古に確認できる実流通媒体**。

- 古いから口承 → 禁止
- 非ネット発祥だから口コミ → 禁止
- 後代研究書があるから書籍 → 禁止

## 8.3. D03

Version Scope内で、実際に受容者へ流通したことを確認できる媒体。

研究DBで見つかることや、現在Web検索可能なこと自体は流通媒体Evidenceではない。

## 8.4. D04

変容Evidenceがないからといって `STABILIZED_CANON` や単発固定へしない。変化を確認できなければ `U` を検討する。

## 8.5. D05 / D06

研究者による記述形式ではなく、伝承が受容者へどう提示され、どの程度の「本当らしさ」を要求するかを見る。

## 8.6. D07

「この伝承がなければ何が説明されないまま残るか」を一文で言語化してから選ぶ。

結果や原因を、意味形成対象と混同しない。

## 8.7. D08とD11

- D08: なぜ問題として立ち上がるかという手掛かり
- D11: 因果系へ入る発動・接触条件

両者を混同しない。

## 8.8. D09

不可解さを理解可能にする認知操作。原因帰属、主体化、類型化、規則化、禁忌化、制度論理化等。

## 8.9. D10

原因を何として世界に置くか。

体験が報告されたことと、超自然存在が実在することを分ける。

## 8.10. D13

「何をするか」をコードし、D15の最終帰結と分ける。

`MANIFEST_ONLY` を資料不足の代用にしてはいけない。

## 8.11. D15

最終的に何の領域が変わるか。

「投稿が止まった」だけで死亡・失踪にしない。

## 8.12. D16

伝承そのものの流通年数ではなく、**発動条件から主作用・主帰結までの時間構造**。

静的命題は `STA` を検討し、非物語型だから `U` にしない。

## 8.13. D17

対処法が確認できないことと「不可避」は別。

不可避には明示Evidenceが必要。対処不明なら `U` を検討する。

## 8.14. D18

- L1: 伝承内部での因果作用
- L2: 読む・聞く・受信する現実側の受容者が、伝承内容上の因果対象になる
- L3: 噂の流通により現実社会で確認可能な行動・制度・市場等の結果が生じる

L3には `X` Evidenceが必要。「影響しそう」では付けない。

通常の説得・不安・行動変化をL2と混同しない。

## 8.15. D19

媒体ではなく社会的流通範囲。

## 8.16. D20

単に「噂を知っている人」ではなく、真相・追加情報・回避情報を偏って保持する主体。

`NO_ONE_KNOWS` は強い主張なので濫用しない。

## 8.17. D21

典拠が実在することと、伝承内容が現実へ固定されていることを分ける。

実在地が舞台なだけなのか、史実・制度・実在物が意味形成モデルの成立に不可欠なのかを見る。

# 9. Step 6 — 00 / 10 横断QA

両ファイルを作成したら、必ず横断的に確認する。

## 9.1. 構造

- Entry_IDが正しい
- ディレクトリ・ファイル名が4桁ゼロ埋め
- tutorialの見出し・項目名・順序を守る
- 独自の追加フィールドを作っていない

## 9.2. `00_contents`

- summaryだけで主要内容を再構成できる
- 一次／ミラー／二次／後代資料を区別している
- 起源と最古確認を混同していない
- 後代異伝を初期形へ遡及していない
- 典拠と内容の対応が追える
- 不確実性が明示されている
- Dコードを混入していない

## 9.3. `10_analysis`

- Version Scopeが明確
- D01〜D21が全てある
- 各DにStatusがある
- `U / NA / C` も理由が書かれている
- 各Dに判定根拠がある
- 各Dに伝承固有の「現れ方」がある
- Primary / Secondaryがコード定義に従う
- ParentとChildが整合する
- D18 L3にX Evidenceがある

## 9.4. 00と10の整合

- `10_analysis` の判定根拠が `00_contents` で確認できる
- `10_analysis` が `00_contents` にない事実を新規作成していない
- Scope外の異伝をコードへ混ぜていない
- `00_contents` の主要不確実性が `10_analysis` のStatusへ反映されている

# 10. Step 7 — GitHub反映・push後検証

原則として **1 Entry = 1 commit** とする。

既存Entryの通常作業では、次の2ファイルだけを同一commitへ含める。

```text
<Entry_ID>_00_contents.md
<Entry_ID>_10_analysis.md
```

片方だけ変更が必要なら1ファイルでもよい。

複数伝承を同一commitへまとめない。テストファイルや一時ファイルをmainへ作らない。

書き込み直前に最新mainを確認する。

commit後は差分を検証し、想定外のファイルが混入していないことを確認する。

push後に必要に応じてファイルを再取得し、最終状態を確認してから完了とする。

# 11. Step 8 — プロジェクト固有の進捗管理

本Stepは汎用workflowではなく、各調査フェーズ固有の管理作業である。

通常の個別伝承作成では、プロジェクト側に進捗管理文書・台帳・control planeがある場合のみ更新する。

## 11.1. A3パイロット49件の場合

A3パイロット49件では、Entry完了後に以下を別commitで更新する。

- `docs/99_work/20260913_A3_pilot_lore_analysis_reconcile.md`

これはパイロット固有の手順であり、後続400件以上の通常作業に自動適用しない。

# 12. 完了条件

以下を満たすまで1 Entryを完了とみなさない。

- Entry境界が妥当
- Entry_IDが正しい
- `*_00_contents.md` と `*_10_analysis.md` が存在
- 00/10の責務分離が守られている
- Evidenceが役割別に整理されている
- summaryが高密度
- 典拠と主要内容が追跡可能
- 起源・最古確認・後代派生を区別
- Version Scopeが明確
- D01〜D21を現行規則で判定
- `U / NA / C` を無理に埋めていない
- 各Dに判定根拠と固有の現れ方がある
- 00と10が相互矛盾しない
- 1 Entry単位のcommitになっている
- commit差分を検証した

# 13. 最重要原則

件数消化を優先しない。

`00_contents` は短い百科事典記事ではなく、**証拠に忠実な高密度の伝承記録**にする。

`10_analysis` はコード一覧ではなく、**21概念次元を通して1つの伝承を読む分析文書**にする。

同時に、文章量そのものを目的化しない。Evidenceが弱い箇所は弱いまま保持し、推測で埋めない。

最終的に重視するのは、後から人間または別のコーダーが、

```text
Evidence
→ 伝承内容
→ Version Scope
→ 分析判断
→ コード
```

を再構成できることである。
