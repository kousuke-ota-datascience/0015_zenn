# 個別伝承レビュー手順書

## 0. この文書の目的

本文書は、`docs/10_each_lore/<Entry>/` 配下の個別伝承について、

- `<Entry_ID>_00_contents.md`
- `<Entry_ID>_10_analysis.md`

をレビューし、その結果を `docs/99_work/review_10_each_lore/` 配下へ保存するための**独立実行可能なレビュー手順書**である。

レビュー担当エージェントは、プロジェクトについて事前知識がないことを前提とする。したがって、レビュー開始時には本文書だけでなく、本文書が指定する正本を必ず読み、既存コード値や過去レビューを正しいものとして前提化しない。

このレビューの目的は、既存ファイルを「それらしく整える」ことではない。以下を検証することである。

1. Evidence / Content layer と Analysis / Coding layer が責務分離されているか。
2. Version Scope が証拠に対して保守的かつ再現可能に固定されているか。
3. D01〜D21 が理論設計、コード体系、コーディング規則に適合しているか。
4. 特に D07〜D17 が、一つの coherent な **sense-making model / 意味形成モデル**として接続しているか。
5. `原資料上の具体的展開 → 分析者の解釈 → コード` を第三者が追跡できるか。
6. 証拠不足、競合、非該当、taxonomy不足が混同されていないか。
7. tutorial の正規フォーマットに準拠しているか。

# 2. レビューの基本単位と保存規則

## 2.1. 1 Entryずつ完結させる

複数Entryを依頼された場合でも、必ず次の単位で処理する。

```text
Entry A の 00 をレビュー
→ Entry A の 10 をレビュー
→ Review_A_00 と Review_A_10 を保存
→ 保存した2ファイルを再取得して確認
→ Entry A 完了
→ 次の Entry B へ進む
```

Entry A のレビュー結果を保存・確認する前に Entry B のレビュー結果作成へ進んではならない。

## 2.2. Entry_ID

`Entry_ID` は**4桁ゼロ埋め**で扱う。

例:

```text
1   → 0001
11  → 0011
59  → 0059
```

対象Entryディレクトリ名や対象ファイル名と照合する。

## 2.3. Review_Seq

`Review_Seq` は**3桁ゼロ埋めのレビュー通し番号**とする。

レビュー格納先:

```text
docs/99_work/review_10_each_lore/<Entry_ID>/
```

1回のレビューサイクルで、00と10には**同じ Review_Seq**を使用する。

```text
Review_<Entry_ID>_00_<Review_Seq>.md
Review_<Entry_ID>_10_<Review_Seq>.md
```

例:

```text
docs/99_work/review_10_each_lore/0011/
  Review_0011_00_001.md
  Review_0011_10_001.md
```

次回レビューは:

```text
Review_0011_00_002.md
Review_0011_10_002.md
```

とする。

### Review_Seqの決定方法

1. `docs/99_work/review_10_each_lore/<Entry_ID>/` を確認する。
2. 既存の `_00_` / `_10_` の両方から最大 `Review_Seq` を取得する。
3. 完結済みレビューサイクルの次番号を使用する。
4. 既存レビューがなければ `001`。
5. 既存ファイルを上書きしない。

最大Seqで片方だけが存在する場合は、過去の未完了レビューの可能性がある。同一レビュー作業の継続であり、対象ファイルの版も同じと確認できる場合のみ欠けた側を同じSeqで補完する。それ以外は次Seqを使用し、過去サイクルが不完全であることを必要に応じて記録する。

# 3. レビューと修正作業を分離する

レビュー担当者は、明示的な修正依頼がない限り、次を行わない。

- 対象の `<Entry_ID>_00_contents.md` を編集しない。
- 対象の `<Entry_ID>_10_analysis.md` を編集しない。
- コード体系を変更しない。
- taxonomy gapを埋めるために新しいChild / Statusを勝手に発明しない。
- Evidence不足を新しい推測で補完しない。

レビューでは、**問題の特定、根拠、影響、修正方向**をレビュー結果mdへ記載する。

新しい外部資料を発見した場合も、レビュー中に元ファイルへ黙って追加しない。必要なら「追加Evidence候補」としてFindingに記録する。

対象Entryについて必ず次を取得する。

```text
docs/10_each_lore/<Entry_Directory>/<Entry_ID>_00_contents.md
docs/10_each_lore/<Entry_Directory>/<Entry_ID>_10_analysis.md
```

# 5. `00_contents` レビュー手順

`00_contents` は **Evidence / Content layer** である。

ここでは「何が資料上確認できるか」を保存し、分析者がどのVersionをコードするか、D07が何か、D10を何とするか等を決めない。

## 5.1. 正規フォーマット確認

現行tutorialに対して、少なくとも以下の構造を確認する。

```text
# 0. INTRODUCTION
## 0.1. 文書の役割
## 0.2. 典拠と証拠上の扱い
### 0.2.1. 一次資料・同時代資料
### 0.2.2. 原文ミラー・転載・復刻資料
### 0.2.3. 二次資料・研究資料

# 1. 伝承内容
## 1.1. summary
## 1.2. 詳細展開
## 1.3. 登場人物・主体
## 1.4. 場所・空間
## 1.5. 物・記号・媒体
## 1.6. 条件・規則・禁忌
## 1.7. 異常・不可解な現象／中心命題
## 1.8. 行動・対応
## 1.9. 帰結・終端状態
## 1.10. 未解決点・不確実性

# 2. 伝承史・異伝
## 2.1. 最古確認
## 2.2. 流通・拡散
## 2.3. 主要な異伝・派生
## 2.4. 変容上の重要点

# 3. 証拠対応
## 3.1. 内容と典拠の対応表
## 3.2. 短い原文引用
## 3.3. 証拠上の保留事項
```

見出し名や順序の差が単なる表記差なのか、Evidenceの追跡可能性を壊しているのかを区別する。

## 5.2. Evidenceの強度と役割

次を確認する。

- 一次資料・同時代資料を、後代まとめより優先しているか。
- 書誌ページ・販売ページ・目録だけから、本文内容を推測していないか。
- 原文ミラー、転載、復刻を一次資料そのものと混同していないか。
- 研究資料が「原資料を引用・復元している」のか、「後代解説しているだけ」なのかを区別しているか。
- URL、書誌、頁、記事日、投稿番号、採録番号等、追跡情報が十分か。
- 本文未実見の場合、その限界を明示しているか。
- 実在する事件・制度・場所が確認できることを、伝承内部の超常因果の証明にしていないか。
- fact-check等で事実性が否定されたことを、伝承が存在しなかった証拠にしていないか。

Evidence roleとして `C / H / X / A` を使っている場合は、役割が適切かも確認する。

- `C`: Content。伝承内容、条件、作用、帰結。
- `H`: History。成立・流通・媒体・変容。
- `X`: External effect。伝承流通により現実側で生じた行動・制度・市場等の効果。
- `A`: Anchor。実在地点、制度、史実等との接続。

## 5.3. `summary` の密度

`1.1 summary` だけを読んでも、第三者が主要な伝承形を再構成できるか確認する。

物語型なら、原則として次が追える必要がある。

```text
発端
→ 異常の顕在化
→ 展開
→ 対応
→ エスカレーション／転換
→ 終端
→ 未解決部分
```

命題・俗信・規則型なら、原則として次が追える必要がある。

```text
対象状況
→ 条件
→ 主張／規則
→ 想定作用
→ 帰結
→ 回避・制御・利用
→ 証拠上の限界
```

ただし、資料にない心理、因果、死亡、失踪、由来、動機、真相を補って物語を完成させてはならない。

「投稿が途切れた」ことを死亡・失踪と変換する等は重大な問題である。

## 5.4. Evidence layerへの分析混入を確認する

`00_contents` に以下が入っていないか確認する。

- `Version_Scope` の採用／除外判断。
- D01〜D21のコード値。
- 「このEntryのPrimaryは〜」等のコーディング判断。
- 「意味形成対象は〜」「意味形成核は〜」等、D07〜D09を確定する分析。
- 「人々は不安を減らすためにこの伝承を作った」等、証拠のない心理・社会過程の断定。
- 後代の代表形を初期形へ遡及する分析。

異伝間でどの構造が共通し、何が変化するかを**記述すること**はできる。しかし、「今回コードするScopeへ入れる／外す」は10側の責務である。

## 5.5. 最古確認と起源を分離する

次を混同していないか確認する。

```text
現在確認できる最古資料 ≠ 実際の起源
公刊年 ≠ 成立年
新聞報道日 ≠ 噂の発生日
古い伝承らしい ≠ 口承起源が確認済み
```

「古い話だから口承」「最古の新聞記事だからその日に生成」といった推測は不可。

## 5.6. 異伝の保持

`00_contents` は、分析Scopeより広く主要異伝を保持してよい。

確認する事項:

- 初期形と後代定型が分離されているか。
- 地域差・媒体差・時代差を一つの固定シナリオへ混ぜていないか。
- 後代に有名になった設定を古いVersionへ遡及していないか。
- 異伝間のConflict、不明点、未確認事項が残されているか。

## 5.7. 証拠対応

重要な内容要素について、`3.1 内容と典拠の対応表` 等から原資料へ戻れるか確認する。

理想的なtraceabilityは、

```text
内容要素
→ 典拠
→ 頁／レス／段落／記事日／採録番号
→ 直接確認できる文言・出来事
```

である。

# 6. `10_analysis` レビュー手順

`10_analysis` は **Analysis / Coding layer** である。

レビューでは、いきなりD01から順にコード名だけを眺めない。まずVersion Scopeを確認し、次に意味形成・因果構造を理解する。

推奨思考順序はworkflowに従い、

```text
D07 → D08 → D09 → D10 → D11 → D12 → D13 → D14 → D15 → D16 → D17 → D18
→ D01 → D02 → D03 → D04 → D05 → D06 → D19 → D20 → D21
```

とする。

レビュー結果の記載順は、対象文書と同様にD01→D21でよい。

## 6.1. 基本情報・書式

最低限以下を確認する。

```text
Entry_ID
伝承エントリ名称
Macro_Category
Entry_Type
Version_Scope
```

- `Entry_ID` は4桁ゼロ埋めか。
- tutorialにない一時作業用項目、R3/R4 checkpoint、旧Excel比較、作業commit等がCoding正本へ混在していないか。
- D01〜D21がすべて存在するか。
- 各次元が原則として次の構造を持つか。

```text
コード値
判定根拠
この伝承における現れ方
必要なら境界・留保
```

コード定義の言い換えだけでなく、当該伝承の人物・物・場所・出来事・規則・帰結へ接続している必要がある。

## 6.2. Version Scope

Version Scopeはコーディングの前提である。

確認する。

- `00_contents` のEvidenceから再構成可能か。
- 最古のcoherentな伝承形が直接観察できるなら、それを優先しているか。
- 最古形が不十分なら、確認可能な最古の安定共有核として保守的に固定しているか。
- 後代設定を「有名だから」という理由で遡及していないか。
- 競合するVersionを無理に一つへ統合していないか。
- 世界ルールが安定して変わる場合、同一EntryのVariationでよいか、別Entryとすべきか検討されているか。

特に以下が変わる場合はEntry境界への影響が大きい。

- 何を説明する伝承か（D07）
- 原因（D10）
- 発動条件（D11）
- 作用対象（D12）
- 作用機構（D13）
- 帰結（D14–D15）
- 回避・制御（D17）

## 6.3. Status

Statusはコード値ではない。

- `D` = Direct
- `I` = Inferred
- `U` = Unknown
- `NA` = Not applicable
- `C` = Conflict

レビュー時は次を確認する。

### D / I

- `D` を付けるだけの直接性がEvidenceにあるか。
- 二次資料の要約や後代整理から合理的に再構成しているなら、`I` が適切ではないか。
- 「内容が明白そう」という理由だけでDにしていないか。

### U

- `U` は**その次元が適用可能だがEvidence不足で判定不能**の場合に使う。
- 「最もありそうなChild」で埋めてはならない。

### NA

- `NA` は資料不足ではなく、伝承構造上その次元自体が成立しない場合に使う。

### C

- `C` は同一Version Scope内部で競合するEvidence / 伝承形を解消できない場合に使う。
- Scopeを適切に分離すれば解消する競合を、安易にCで保持していないか確認する。

## 6.4. Primary / Secondary

H3等、Primary / Secondaryを持つ次元ではcoding rulesに従う。

原則:

- D / I の場合、Primaryは1つ。
- Secondaryは0〜2個。
- Primaryは、その次元の中心質問へ最も直接答え、Entry構造を最も規定するChild。
- SecondaryはPrimaryだけでは失われる**独立した追加構造**がある場合のみ。
- 「少し関係する」「説明文に出てくる」だけではSecondaryへ入れない。

tie-breakは原則として、

```text
中心質問への直接性
→ Evidence強度
→ sense-making構造上の不可欠性
→ unsupported assumptionを増やさない保守性
```

の順で考える。

## 6.5. コードの存在とParent整合

各コードについて、`20_urban_legend_parent_child_code_system.md` に実在するかを確認する。

- 存在しないChildを使っていないか。
- Childに対応するParentが正しいか。
- コード名ではなく定義本文に適合しているか。
- 近いコードがあるというだけで無理に写像していないか。

# 7. sense-making / 意味形成レビュー — 最重要項目

## 7.1. 本研究が直接コードするもの

本研究では、

> **1伝承エントリ = 1意味形成モデル**

として扱う。

直接コードする主対象は、心理・社会過程そのものではなく、伝承に符号化された **sense-making model / artifact** である。

したがって、

> 「人々が実際に不安を解消するためにこの伝承を作った」

等の形成動機を、会話ログ、時系列、版変化、当事者発言等なしに断定してはならない。

レビューすべきなのは、伝承がどのような説明・因果・規則・予測・対処の構造を持つかである。

## 7.2. 基本変換

意味形成は、概ね以下の変換として読む。

```text
異常・不可解・不確実な入力
↓
何が問題なのかを切り出す
↓
手掛かりを選ぶ
↓
命名・分類・原因帰属・主体帰属・パターン化・規則化等
↓
将来予測・禁忌・回避・利用・検証の規則
↓
共有可能な世界モデル
```

説明が科学的に真である必要はない。誤った因果、超自然説明、疑似相関でも、伝承内部で理解・予測・対処のモデルを作っていれば分析対象になる。

また、謎を完全に解消する必要もない。「原因は不明だが、この条件では危険」「正体不明だが、ここに何かいる」という**不可知性を保持した世界モデル**もあり得る。

## 7.3. D07 / D08 / D09を厳密に分ける

### D07 — 意味形成対象

問い:

> **この伝承がなければ何が説明されないまま残るか。**

D07は「説明を要求する何か」である。

作用結果や原因主体そのものを、機械的にD07へ置かない。

### D08 — 意味形成契機

問い:

> **何を手掛かりに、その問題が問題として立ち上がるか。**

目撃、証言、反復、物的痕跡、文書、事故履歴、根拠未提示の主張等が候補になる。

### D09 — 意味付与操作

問い:

> **不可解・不確実なものを、どの認知操作で理解可能にするか。**

例:

- 命名
- 類型化
- 原因帰属
- 主体帰属
- 相関規則化
- 予兆化
- 禁忌化
- 回避規則化
- 制度解釈
- 由来化
- 不可知性保持

### 典型的な誤り

```text
D13で発生する作用
→ それをD08の先行手掛かりとして再投入
```

のように、モデル内部の結果を意味形成の入力側へ逆流させると論理循環が生じる。

レビューでは必ず、

```text
D07 → D08 → D09 → D10以降
```

が因果・論理上循環していないか確認する。

## 7.4. D09とD10を分ける

- D09 = **どう理解可能にするかという操作**。
- D10 = **その結果、原因を何として世界に置くかという存在論**。

例:

```text
「意思ある何かがやった」と主体化する = D09
その主体を「幽霊」と置く = D10
```

主体化したから自動的に `YOKAI_ENTITY` になるわけではない。

## 7.5. D08とD11を分ける

- D08 = 問題化の手掛かり。
- D11 = 伝承内部の因果系へ入る発動・接触条件。

例:

```text
「この場所では事故が続く」という反復証言 = D08
その場所へ入ると怪異に遭う = D11
```

「問いに答えると結果が分岐する」場合、その回答が本当に因果系への入口なのか、すでに怪異接触後の分岐条件なのかを確認する。

# 8. D10〜D17の因果モデルQA

## 8.1. D10 因果源存在論

- Evidenceが単に「異常が報告された」ことしか示さないのに、幽霊・妖怪・異世界等へ強く固定していないか。
- 後代解釈を初期Scopeへ遡及していないか。
- 強い存在論コードは、その存在論がScope内で明示・安定している場合に限る。

## 8.2. D11 発動・接触条件

D11は**因果系への入口**である。

- ただの日常行動を再現的triggerとして過剰評価していないか。
- 本人の操作が反復可能な発動条件ならmanual/action系を検討する。
- 本人の選択によらない偶発遭遇ならpassive系を検討する。
- 既存taxonomyに必要な発動条件がない場合、近いpassiveコードへ押し込まずtaxonomy gapを検討する。

## 8.3. D12 → D13 → D15 causal QA

必ず一本の因果列として読む。

```text
D12 誰／何に
→ D13 何をして
→ D15 最終的に何の領域が変化するか
```

確認する。

- D12は主人公というだけで選んでいないか。
- D12はPrimary D13の**直接対象**になっているか。
- D13は伝承で実際に行われる主作用か。
- D15はD13から到達する終端領域か。
- 中心事象がこの三次元から脱落していないか。

### `MANIFEST_ONLY` の注意

`D13.MAN.MANIFEST_ONLY` は、

> 現れる／認識されるが、追加作用を必須としない

場合のコードである。

「適切な作用コードが見つからない」「Evidenceが弱い」ことのfallbackとして使ってはならない。

伝承の中心が消失、追跡、攻撃、移動、情報付与等であるのに、それを落として「顕現のみ」にしていないか確認する。

## 8.4. D14 / D15

- 不気味だから自動的にNegativeにしない。
- 攻撃があるから自動的に死亡へしない。
- 投稿停止・その後不明を死亡・失踪へ変換しない。
- 最終的に不確実性が保持される場合は `KNW.UNCERTAINTY_PRESERVED` 等の適合可能性を検討する。

## 8.5. D16

D16は因果系内部の時間構造であり、伝承が何十年流通したかではない。

- 単発観測
- 単一エピソード
- 段階進行
- 期限
- 遅延
- 反復
- 連鎖

等を、作用・帰結の時間編成として確認する。

## 8.6. D17

- 資料に回避法が書かれていないことと「回避不能」は同じではない。
- `NO_KNOWN_ESCAPE`、`FIXED_OUTCOME` 等の強いコードは明示Evidenceを要求する。
- 利用・制御法がある場合、その方法がScope内で安定しているか確認する。
- 「忘れる」等、既存Childに直接表現できない安定構造がある場合、近似コードへ押し込まずtaxonomy gapを検討する。

# 9. D01〜D06 / D18〜D21の重点QA

## D01 生成年代

最古確認資料を生成時期へ変換しない。

## D02 最古確認流通媒体

問いは「現在のEvidenceで実際の流通を最も古く確認できる媒体」である。

- 起源媒体を推測しない。
- 「古い伝承だから口承」を禁止する。
- 研究論文に記載されていることと、伝承が研究論文で流通したことを混同しない。

## D03 確認流通媒体ポートフォリオ

**Version Scope内**で実際に確認できる流通媒体を扱う。Scope外の後代媒体を足さない。

## D04 生成・変容パターン

時間的変容を示すHistory Evidenceが必要。

単に複数異伝が並存するだけで、どのように変化したかを断定しない。

## D05 提示形式

伝承が受容者へどう提示されるかを見る。Evidenceを記録した資料の形式と混同しない。

## D06 真実性提示

研究者が真偽をどう判断するかではなく、**伝承自身がどの「本当らしさ」を要求するか**を見る。

- 「都市伝説と呼ばれている」から自動的に `真偽未確定` にしない。
- 直接体験談の「私は見た」という提示と、報道・研究側の懐疑的ラベルを区別する。

## D18 作用レイヤー

特にL3を厳密に確認する。

- L1: 伝承内部の因果。
- L2: 現実側受容者が伝承内容上の因果対象へ入る自己適用。
- L3: **伝承・噂の流通によって、現実社会に行動・制度・市場等の結果が生じたことを示すX Evidence**。

個別事件への警察対応そのものは、それが「噂の流通による二次効果」でなければL3根拠ではない。

## D19 流通範囲

Scope期間・Evidenceが支持する範囲を超えて「全国」等へ拡張しない。

## D20 特権情報保持者

強いコードを欠如Evidenceから作らない。

- `NO_ONE_KNOWS` は「資料に答えがない」という意味ではない。
- `NO_HIDDEN_TRUTH` は「特権保持者を確認できない」だけでは足りない。
- 体験者本人が詳細を知ることと、「真相を知る特権保持者」であることを区別する。

## D21 現実アンカー

Evidence資料の所在地ではなく、**Scoped Contentそのものがどの程度実在世界へ固定されるか**を見る。

# 10. taxonomy gapの扱い

これは必須QAである。

## 10.1. Evidence不足とtaxonomy不足を分ける

次の二つは別である。

```text
A. 何が起きるかEvidenceが足りない
B. 何が起きるかは明確だが、表現できるChildがない
```

Aは `U` 候補になり得る。

Bは**taxonomy gap**であり、通常のEvidence `U` と同一視してはならない。

## 10.2. レビュー時の処理

対象10がtaxonomy gapを認識しながら、

- `U` として保存している
- 「一番近い」Childへ無理に写像している
- 定義を拡張して既存Childへ押し込んでいる

場合はFindingとする。

レビュー担当者は新しいコードやStatusを勝手に作らない。

レビュー結果には、

> Evidenceはあるがtaxonomyに表現能力がない。Entry単独の修正では完結せず、コード体系／保存規則側へのエスカレーションが必要。

と記録する。

単一Entryだけを理由にbaseline taxonomy変更を確定しない。

# 11. 00 / 10 横断QA

00と10を別々に読むだけで終わらせない。

次を確認する。

1. `Version_Scope` が00のEvidenceから再構成できるか。
2. 10の各 `判定根拠` が00の具体的内容・典拠へ戻れるか。
3. 00で未確認と明記した事項を、10が確定値として使っていないか。
4. 00が保持する後代異伝を、10がScopeへ無断混入していないか。
5. 10のD07〜D17を読むと、同じ一つの伝承Versionの世界モデルになっているか。
6. D18 L3等で使うX Evidenceが00に記録されているか。
7. D01〜D06の来歴・提示と、D07〜D17の内容分析で異なるVersionを混ぜていないか。

理想は、

```text
00の具体的Evidence
→ Version Scope
→ 分析者の解釈
→ D01〜D21コード
```

を第三者が追える状態である。

# 12. Findingの重大度

各Findingには `Major / Moderate / Minor` のいずれかを付ける。

## Major

次のいずれかに該当する場合を基本とする。

- Version Scopeを変える可能性が高い。
- D07〜D17のsense-making / 因果モデルを変える。
- Primary code、Status、Entry境界等の分析結論へ直接影響する。
- EvidenceとAnalysisの責務混同により、分析再現性が大きく損なわれる。
- taxonomy gapを誤コードで隠している。
- tutorialから大きく逸脱し、Evidence traceabilityを阻害している。

## Moderate

- 一部次元のコード／Statusへ影響し得るが、Entry全体のモデルは維持される。
- Evidence directness、Secondary、局所的Scope根拠等の再確認が必要。
- 文書構造や説明不足が再現性を下げるが、現有Evidenceは利用可能。

## Minor

- 4桁ゼロ埋め、表記、見出し、軽微なフォーマット等。
- 分析結果やEvidence解釈を変えない局所修正。

## 最終判定

原則として未解決Findingの最大重大度に合わせる。

```text
Findingなし              → 問題なし（Pass）
Minorのみ                 → 要修正（Minor）
Moderateあり、Majorなし   → 要修正（Moderate）
Majorあり                 → 要修正（Major）
```

重大度は「文章量」ではなく、研究結果・再現性への影響で決める。

# 13. Reviewファイルの書き方

レビューは、単なる感想や修正文案の羅列にしない。

各Findingは原則として次を含む。

```text
何が現在書かれているか
→ 何が規則・理論と衝突するか
→ なぜ分析上問題か
→ どの方向へ修正すべきか
```

コード変更を提案する場合、Evidenceが十分でなければ確定値として断言せず、

- 第一候補
- 再検討候補
- Evidence追加後に判定
- taxonomy gap候補

等と書き分ける。

## 13.1. 事実・解釈・作業仮説を区別する

レビュー本文では次を混同しない。

- **事実:** 対象ファイルに実際に書かれているコード、Evidence、文言。
- **解釈:** 正本の規則に照らしたレビュー判断。
- **作業仮説:** 再コーディング時に検証すべき代替モデル。

sense-making再構成案等を記載する場合は、「確定コードではなく作業仮説」と明示する。

# 17. レビューで禁止するショートカット

以下を行ってはならない。

- 有名な後代設定を初期Versionへ入れる。
- 「古いから口承」「怪談だから幽霊」等、ジャンル印象でコードする。
- Evidence不足を「最もありそうなコード」で埋める。
- taxonomy gapを `U` と同一視する。
- taxonomy gapを近似Childで隠す。
- `MANIFEST_ONLY` を作用コード不明時のfallbackにする。
- 回避法が書かれていないことを「回避不能」とする。
- 体験者が詳細を知ることを「真相を知る特権保持者」と同一視する。
- 報道側・研究者側の真偽評価をD06へそのまま移す。
- 一件の警察・行政対応を自動的にD18 L3とする。
- 伝承がsense-making modelを持つことから、作者・受容者の心理的動機を推定する。
- 00と10を別VersionのEvidenceでコードしていることを見逃す。
- レビュー結果を保存せず次Entryへ進む。
